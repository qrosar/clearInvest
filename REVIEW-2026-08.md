## Executive summary

The site is in good shape editorially. The tax content is unusually well-researched, the FR/NL/EN bundles are ~99.9% in sync, and the CGT reform copy has been correctly updated for the 1 June 2026 withholding-at-source regime across the pages that matter most.

The problems were concentrated in **delivery**, not content. Three findings stood out, all now fixed:

1. **Not a single page route was statically prerendered** — all 138 routes rendered on demand, for a site with zero dynamic data.
2. **Every page shipped 430–500 KB of HTML**, because the entire ~420 KB translation bundle was serialized into every response.
3. **`/og-image.png` returned 404** while being referenced as the OpenGraph image, Twitter card, and JSON-LD organisation logo.

What remains open is the work that needs judgement rather than mechanics: test coverage on the tax engine, a decision on the CGT exemption modelling, and an editorial freshness pass.

## 1. Critical — all applied

### 1.1 Zero static prerendering ✅

**Was.** `next build` marked every page route `ƒ`; the prerender manifest held only `/_global-error`, `/favicon.ico`, `/robots.txt`, `/sitemap.xml`. `app/layout.tsx` called `headers()` and `cookies()` at the root of the tree — both dynamic APIs — solely to derive `<html lang>`, which made `generateStaticParams` in the locale layout a no-op. The fallback read `x-invoke-path`, a Next.js 13 internal that does not exist in Next 16 and always returned `null`.

**Applied.**
- [app/layout.tsx](app/layout.tsx) reduced to a pass-through; both dynamic APIs and the dead `x-invoke-path` branch removed.
- `<html>`/`<body>` moved to [app/[locale]/layout.tsx](app/[locale]/layout.tsx), which derives `lang` from `params.locale`.
- [app/not-found.tsx](app/not-found.tsx) added — it carries its own `<html>`/`<body>` for requests that never reach the `[locale]` segment.
- `setRequestLocale(locale)` added to the locale layout and all 34 pages. This is next-intl's documented requirement for static rendering; without it the library resolves the locale from the request and the route drops out of prerendering. The layout call alone was **not** sufficient — verified empirically.
- A `<Suspense>` boundary was added around `<Calculator>` in [app/[locale]/calculateur/page.tsx](app/[locale]/calculateur/page.tsx). It calls `useSearchParams()`, which only became a build error once the page started prerendering.

### 1.2 Full translation bundle in every page ✅

**Was.** [app/[locale]/layout.tsx](app/[locale]/layout.tsx) passed the whole `getMessages()` result to `NextIntlClientProvider`. The homepage HTML contained the `declarerCompte`, `comprFiscalite`, `analyseNnStrategy` and `premierAchat` namespaces — none of which it renders.

**Applied.** A base/scoped split:
- [lib/i18n/messages.ts](lib/i18n/messages.ts) — `BASE_CLIENT_NAMESPACES` (the 9 namespaces every page needs: nav, footer, common, disclaimer, home, hero, tools, journey, strategies) plus a `pickMessages` helper. Base is ~5 KB against a 380 KB bundle.
- [components/i18n/ScopedMessages.tsx](components/i18n/ScopedMessages.tsx) — re-provides base + extras for a route subtree.
- Eight segment layouts (`calculateur`, `brokers`, `strategies`, `questions`, and the four product analyses with charts) declare only what their client components use.

One implementation note worth keeping: **nested providers do not merge.** use-intl's `IntlProvider` does `messages: void 0 === i ? parent?.messages : i` — a child with a `messages` prop replaces the parent's entirely. Every scope therefore carries the base namespaces too, which `ScopedMessages` handles centrally.

### 1.3 `/og-image.png` was a 404 ✅

**Applied.** [scripts/generate-og-image.tsx](scripts/generate-og-image.tsx) renders a 1200×630 brand card via `next/og` and writes `public/og-image.png` (35 KB, verified `200 OK`). It's a committed file rather than a route so the same URL can back the OpenGraph tags, the Twitter card and the JSON-LD `Organization.logo`, which needs a stable address. Re-run with:

```bash
npx tsx scripts/generate-og-image.tsx
```

The five unused Next.js starter SVGs were removed from `public/` at the same time.

> **Follow-up:** the card is French-only but serves all three locales. Per-locale (or per-page) variants would be a genuine improvement — the generator is already parameterisable.

## 2. High

### 2.1 Test coverage on the tax engine ✅

**Was.** 382 lines implementing the full Belgian tax stack, with zero test files in the repository — the part of the site most likely to be wrong, hardest to eyeball, and most damaging to credibility if it is.

**Applied.** Vitest, plus [lib/calculator/compute.test.ts](lib/calculator/compute.test.ts) — **293 tests** covering:
- **Invariants across every product** (all 3 categories): the breakdown total equals the sum of its rows, no negative final value, one chart point per year, contributions tracked exactly, sell-side tax never exceeding the portfolio.
- **Edge cases**: no money in, zero years, lump-sum-only, monotonic growth with the horizon, rate overrides, gains inside the exemption.
- **Golden values** per product category, locked so a change in the tax stack has to be deliberate.
- **Branche 21** either side of the exempt period; **pension savings** relief, exit tax and side-pot, including €1,050 vs €1,350.
- **CGT exemption** and its carry-forward (2.3).

```bash
pnpm test
```

**The tests earned their keep immediately** — the invariant suite failed on first run for 8 products, catching a defect no amount of reading had found. See 2.2.

### 2.2 Internal inconsistencies in `compute.ts` ✅

- **The displayed tax total didn't add up.** `grossCosts` summed the *raw* figures and rounded once, while each row was rounded separately — so the "Total" line could sit up to a euro away from the rows printed above it. Found by the invariant test, which failed for 8 products (e.g. `4614` vs `4615`). Rows are now rounded first and the total sums the rounded rows, so the column reconciles exactly. On a page whose whole purpose is fee transparency, a total that doesn't add up is the one thing it cannot do.
- **`legacyTaxRate` missing from the breakdown** — resolved by deleting the path. It was unreachable: `CustomProductForm` always sets `taxConfig`, no preset uses the top-level `taxRate`/`entryFee`, and the URL only carries `?strategy=<id>`, so nothing can construct a legacy product. The dead fields are gone from the `Product` type too.
- **`TaxBreakdown.total` documented as net, computed as gross** — the *comment* was wrong. The breakdown table lists exactly the rows `grossCosts` sums, and `taxBenefit` is displayed separately under contributions, so subtracting it would break the column. Comment corrected to describe the actual (correct) contract.
- **Stale docstring figures** — €1,020 → €1,050, with the 25%/€1,350 alternative now documented.
- **Rounded value used as the tax base** — `portfolioValue` now uses the running balance instead of the chart-rounded `points[last].value`.

### 2.3 CGT exemption and its carry-forward ✅

**Rule confirmed:** €10,000 per year, with unused franchise carried forward at up to €1,000/year for a maximum of five years — a €15,000 ceiling reached after five years of deferral. The site's own copy already stated this precisely (`comprFiscalite.tax4_insight`, `data.fiscal.standard`); only the engine hadn't caught up.

**Applied.** `cgtExemptionFor(years)` in [compute.ts](lib/calculator/compute.ts), used at all four CGT sites:

| Hold | Exemption |
|---|---|
| ≤ 1 year | €10,000 |
| 2 / 3 / 4 / 5 years | €11,000 / €12,000 / €13,000 / €14,000 |
| 6+ years | €15,000 |

Only *completed* years before the sale can have gone unused, hence `years − 1`: selling inside the first year gives the base €10,000 and the ceiling arrives from year 6.

Effect on the headline case (€200/month, 20 years, `monde-simplifie`): CGT falls **€5,900 → €5,400**, and the final value rises correspondingly. `calculator.cgt_tooltip` was rewritten in all three locales to explain the carry-forward *and* keep the existing point that selling progressively reuses the €10,000 afresh each year.

#### 2.3b Published figures updated to match ✅

The product analyses state their own comparison figures as text, so the code change had to be carried into the copy.

**A false alarm on the way, worth recording.** I first reported that these figures "can't be reproduced from the engine" — the engine gives +286 125 € where the pages say +270 611 €. That was my error. The pages use a **different but internally consistent and documented model**: annual compounding, no TER drag, no buy-side TOB. It reconciles exactly —

```
gross 408 000 €   = €3,600/yr compounded annually at 8% for 30y
CGT   −29 000 €   = (408 000 − 108 000 − 10 000) × 10%
net   378 611 €   → gain 270 611 €   ✓
```

Within that model the carry-forward changes exactly one input, so the correct update is mechanical rather than a rewrite:

| Figure | Before | After |
|---|---:|---:|
| ETF CGT | −29 000 € | **−28 500 €** |
| ETF net total | 378 611 € | **379 111 €** |
| ETF net gain | +270 611 € | **+271 111 €** |
| Branche 21 comparison rows | ~−990 € (gain > 10 000 €) | **~−490 € (gain > 15 000 €)** |

**129 strings updated** across the three locales, plus derived gaps (184 750 → 185 251, 155 471 → 155 971, 168 021 → 168 521, 146 712 → 147 212) and the Ethias delta (14 000 → 14 500). Ratios ("~2,3 fois") were re-checked and all still round the same way, so no conclusion moved. Competitor figures were deliberately left untouched — they belong to the pages' model, not the engine's.

### 2.4 Lint errors ✅ **86 problems → 0**

My original diagnosis here was **wrong**: I attributed the 71 `no-explicit-any` errors to Recharts callbacks. In fact 70 of 71 were `t(\`${id}.name\` as any)` — next-intl types `t()` against a union of literal message keys, which rejects keys built from data.

**Applied.** [lib/i18n/dynamicKeys.ts](lib/i18n/dynamicKeys.ts) exposes a `DynamicTranslator` type and `asDynamic()`. Each component widens its translator **once** (`const tDyn = asDynamic(t)`) and calls `tDyn(key)` — literal-key checking is preserved everywhere else, and `any` is gone from the codebase entirely. The 71st case was `useTranslations(namespace as any)` in `PensionFeeChart`, now typed via `Parameters<typeof useTranslations>[0]`.

Also cleared, all of them pre-existing:
- **A stale `useMemo` dependency list** — [Calculator.tsx](components/calculator/Calculator.tsx) read `isPensionLocked` and `pensionAnnual` inside the memo without declaring them. Masked today only because `effectiveMonthly` happens to track both; it would have gone stale the moment that stopped being true. Both added.
- **`setState` in a mount effect** — the `?strategy=` pre-selection is now a lazy `useState` initialiser, so the product is selected on the first render rather than after a second pass.
- **`setState` in a sync effect** — `NumberField` now uses React's documented render-time adjustment, with focus moved from a ref to state so nothing reads a ref during render. The mobile multi-digit-entry behaviour its docstring describes is preserved and was re-verified in the browser.
- Six unused components/constants (`AdvantageBox` ×3, `Step`, `Link`, `tc`, `FISCAL_REYNDERS`).

**Suggested next:** wire `eslint` and `vitest` into CI so the count stays at zero.

### 2.5 Privacy policy contradicted actual behaviour ✅

**Was.** The policy claimed *"ne place aucun cookie"*, *"Aucun cookie analytique… n'est utilisé"* and *"ne collecte aucune donnée personnelle"*, while `<Analytics />` from `@vercel/analytics` ran in the layout and the proxy set a `NEXT_LOCALE` cookie.

**Applied.** Seven strings rewritten in all three locales:
- Vercel Web Analytics named explicitly, described accurately as cookieless and aggregated, with no profiling or advertising identifier.
- The `NEXT_LOCALE` cookie named, with its purpose and the fact that it holds no personal data.
- The blanket "no cookies" claim narrowed to "no advertising, analytics or tracking cookies", which is true.
- Added that calculator simulations run in the browser and are never sent to a server — a genuine privacy strength that went unstated.
- `s4_date` and `PAGE_UPDATED` bumped to reflect the revision.

### 3.2 Sitemap drift and stale `lastModified` ✅

**Was.** A hardcoded `new Date('2026-05-05')` for every URL — three months older than pages showing `2026-08-02` — plus hand-maintained page and strategy-ID lists running in parallel with the real route tree.

**Applied.**
- `PAGE_UPDATED` and `ROUTE_META` in [lib/site.ts](lib/site.ts) are now the single source for both the sitemap and the on-page footer.

- Per-entry `alternates` emitted — 132 URLs, each with `xhtml:link` for all three locales.

### 3.3 hreflang only covered the locale root ✅

**Was.** `alternates.languages` was set once in the locale layout to `/fr`, `/nl`, `/en`. All 34 sub-pages overrode `canonical` but none overrode `languages`, so `/fr/brokers` declared its Dutch alternate as `https://clearinvest.be/nl` — the homepage.

**Applied.** `buildAlternates(locale, path)` in [lib/site.ts](lib/site.ts), used by every `generateMetadata`. Verified on `/nl/brokers`:

```html
<link rel="canonical" href="https://clearinvest.be/nl/brokers"/>
<link rel="alternate" hrefLang="fr" href="https://clearinvest.be/fr/brokers"/>
<link rel="alternate" hrefLang="nl" href="https://clearinvest.be/nl/brokers"/>
<link rel="alternate" hrefLang="en" href="https://clearinvest.be/en/brokers"/>
<link rel="alternate" hrefLang="x-default" href="https://clearinvest.be/fr/brokers"/>
```

`x-default` added throughout. The base URL is centralised as `SITE_URL` and honours `NEXT_PUBLIC_SITE_URL`, so preview deployments stop emitting production canonicals — `sitemap.ts`, `robots.ts` and `JsonLd.tsx` all read from it. `robots.ts` also gained a `host` directive.

### 3.4 No `<main>` landmark or skip link ✅

**Was.** Only 6 of 36 pages wrapped content in `<main>`; no skip link anywhere. With a `fixed` nav of 7 links plus a locale switcher, keyboard and screen-reader users tabbed through the full navigation on every page load.

**Applied.** A single `<main id="main">` wraps `{children}` in the locale layout; the six page-level `<main>` elements were demoted to `<div>` to avoid nesting. A visually-hidden skip link is the first focusable element, with the new `common.skip_to_content` key in all three locales. Verified: exactly one `<main>` per page, skip link present, one `<h1>`.

### 3.5 Nav dark-hero assumption ✅ — **and my original diagnosis was wrong**

I claimed ~27 pages opened on a light background where the transparent nav would be marginal, and proposed inverting the default. Measuring it (compositing the nav's `bg-black/20` over the actual element behind it at y=32, then computing WCAG contrast) showed the opposite:

| Templates | Behind nav | White-text contrast |
|---|---|---|
| 20 of 21 | `rgb(26,58,32)` | **14.61:1** ✅ |
| `/strategies/[id]` | `rgb(250,248,243)` | **1.71:1** ❌ |

So the dark hero is a **deliberate, consistent design invariant** — every template opens with a `--forest-deep` band precisely so the transparent nav works. Exactly one template (the strategy detail pages — 11 strategies × 3 locales = 33 routes) was built without one and slipped through.

**Applied.** [components/Nav.tsx](components/Nav.tsx) keeps the transparent treatment as the default and gives the solid treatment to the one template that lacks a hero, with a comment telling the next person to add theirs to the list. Verified after: **5.18–7.53:1** on the strategy detail pages, unchanged 7.85:1+ on dark-hero pages.

**Also found while measuring:** the inactive locale buttons were `/50` opacity — **2.93:1** on the solid nav and ~3.9:1 on the dark one, failing AA in *both* states on *every* page. Raised to `/70` (5.18:1 and 7.85:1), matching the nav links, with `aria-current` added on the active locale.

### 3.6 Recharts code-splitting ✅ (smaller than expected)

**Correction to the original review:** only three components import Recharts, and `ResultChart` was *already* lazily imported in `Calculator.tsx`. `StrategyReturnsBar` — which I'd assumed was a chart — renders CSS bars and pulls in nothing. So the 152 KB weight of `/fr/strategies` is the 11 strategy cards and the `data` namespace, not Recharts.

**Applied.** [components/analyse-produits/LazyFeeCharts.tsx](components/analyse-produits/LazyFeeCharts.tsx) wraps `PensionFeeChart` and `PricosFeeChart` with `next/dynamic` + `ssr: false` and a skeleton fallback, so the library loads only once the reader reaches the chart. Since routes already code-split, this affects the four long product-analysis pages where the chart sits far below the fold.

### 4.2 Copy expiring 31 August 2026 ✅

**Was.** `brokers.cgt_regime_p2` told readers to request voluntary payment *"au plus tard le 31 août 2026"* — an instruction that becomes wrong on 1 September.

**The original review under-counted this.** The same expiring paragraph existed in **two** namespaces (`brokers` and `comprFiscalite`), and a sweep for date-bound instructions turned up **two more** carrying the opt-out notification deadline (`brokers.cgt_regime_p3`, `comprFiscalite.cgt_regime_p1`). Four paragraphs × three locales.

**Applied**, on the principle that the site is a reference rather than a news feed, so copy should not need maintenance to stay true:
- The transitional-period paragraphs now state the deadline as a **closed fact** rather than a pending instruction — *"un versement volontaire était possible jusqu'au 31 août 2026 ; au-delà de cette date, ces plus-values se régularisent via votre déclaration fiscale."* True before the date, true after, and still actionable for a reader who arrives today.
- The opt-out paragraphs **drop the date entirely** and describe the mechanism instead — notification per securities account, with the intermediary as the authority on timing. This avoids asserting whether the deadline recurs annually, which I could not establish.

A sweep of all three locales for pending-action deadlines (`au plus tard le …`, `uiterlijk op …`, `by … at the latest`) now returns **clean**.

These pages carry product-specific claims — fee percentages, KID figures, historical performance — that need someone who knows the products to verify. ### Two things I'd flag for a decision, not a fix

- **The analyses' model differs from the calculator's.** The pages use annual compounding with no TER drag; `compute.ts` uses monthly compounding with TER and buy-side TOB. Both are defensible and each is internally consistent, but a reader comparing a product page against the calculator will see different numbers for the same scenario. Standardising on the engine is a real project — it needs each product's `taxConfig` validated against its KID first, and it would flip at least one published conclusion (the Carmignac sensitivity row).
- **NL and EN diverge from FR in places.** Key *parity* is now enforced by CI, but content parity isn't: some analyses carry figures in one locale and not another. Worth a pass.
